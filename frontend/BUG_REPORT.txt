================================ CRITICAL ======================================

BUG #1 — DATA LOSS ON EVERY PRODUCTION RESTART
File:       backend application-prod.properties
Line:       spring.jpa.hibernate.ddl-auto=create
Severity:   CRITICAL
Description:
  The production Spring profile uses ddl-auto=create, which DROPS and
  RECREATES all database tables on every application restart. This means
  every time the backend is restarted or redeployed, ALL production data
  (users, events, orders, tickets, companies) is permanently destroyed.
Fix:
  Change to spring.jpa.hibernate.ddl-auto=validate (or "none") in the
  production profile. Use Flyway or Liquibase for schema migrations.

--------------------------------------------------------------------------------

BUG #2 — HARDCODED DATABASE CREDENTIALS IN PRODUCTION CONFIG
File:       backend application-prod.properties
Severity:   CRITICAL
Description:
  PostgreSQL credentials are hardcoded in plain text:
    - Username: postgres
    - Password: Pass_1234
  These are committed to source control and visible to anyone with repo
  access. This violates basic security practices.
Fix:
  Externalize credentials to environment variables or a secrets manager
  (e.g., AWS Secrets Manager, HashiCorp Vault, or at minimum OS env vars).
  Example: spring.datasource.password=${DB_PASSWORD}

--------------------------------------------------------------------------------

BUG #3 — MERGE CONFLICT MARKERS IN PRODUCTION SOURCE CODE
File:       frontend/src/pages/admin/AdminPage.tsx (AdminUsersTable component)
Severity:   CRITICAL

    ... code variant A ...

================================ HIGH ==========================================

BUG #4 — ORDER HISTORY PAGE: INFINITE LOADING SPINNER ON AUTH FAILURE
File:       frontend/src/pages/orders/OrderHistoryPage.tsx
Severity:   HIGH
Description:
  When initUser() fails (no token, invalid token, API error), the error
  state is set BUT isLoading is never set to false. isLoading is initialized
  to true and only set to false inside fetchOrdersAndEvents(), which requires
  userId to be successfully set first. When auth fails, userId is never set,
  so isLoading stays true forever.

  Result: The user sees "Retrieving Records..." loading spinner forever
  with no error message and no way to recover. The error state IS set
  correctly but is hidden behind the loading guard.
Fix:
  Add setIsLoading(false) in the catch block of initUser(), or restructure
  the loading state to be independent of the data fetch pipeline.

--------------------------------------------------------------------------------

BUG #5 — CHECKOUT PAGE: NO DOUBLE-CLICK PROTECTION ON PAYMENT BUTTON
File:       frontend/src/pages/orders/CheckoutPage.tsx
Severity:   HIGH
Description:
  The "Authorize & Pay" button has no debounce, throttle, or disable-on-click
  protection. The processState is set to 'processing' inside handlePayment(),
  but handleInitiatePayment() (which calls it) validates card details and
  checks event status BEFORE calling handlePayment(). During that async
  validation window, a user who double-clicks or has a slow connection could
  trigger two concurrent checkout() API calls.

  With the real payment gateway (prod profile), this could result in the
  user being charged twice for the same order.
Fix:
  Disable the payment button immediately when handleInitiatePayment() is
  called (before validation), or add a guard flag that prevents concurrent
  invocations.

--------------------------------------------------------------------------------

BUG #6 — AUTH CONTEXT: GUEST ENTRY FAILURE CAUSES UNHANDLED PROMISE REJECTION
File:       frontend/src/context/AuthContext.tsx (refreshPermissions)
Severity:   HIGH
Description:
  When authApi.guestEntry() fails inside refreshPermissions(), the error
  propagates as an unhandled promise rejection from the useEffect. The
  try/finally block ensures setLoading(false) runs, but no error state is
  surfaced to the user. The app enters a broken auth state silently — no
  token, no permissions, no error message.

  This affects ALL users when the guest entry endpoint is down, since every
  new visitor and every expired-token user goes through this path.
Fix:
  Add a catch block in refreshPermissions() that sets an error state.
  Display a "service unavailable" message to the user when auth bootstrap
  fails completely.

--------------------------------------------------------------------------------

BUG #7 — AUTH CONTEXT: loginWithToken() PERSISTS STATE BEFORE PERMISSIONS SUCCEED
File:       frontend/src/context/AuthContext.tsx (loginWithToken)
Severity:   HIGH
Description:
  loginWithToken() immediately calls:
    localStorage.setItem(TOKEN_KEY, newToken)
    localStorage.setItem(USER_ID_KEY, userId)
    setToken(newToken)
    connectPresence(newToken)

  ...BEFORE calling authApi.getPermissions(newToken). If getPermissions()
  fails, the token and userId are already persisted to localStorage. On
  next page load, the app will try to use this potentially invalid token,
  fail silently, and fall back to guest — losing the user's login context
  without explanation.
Fix:
  Only persist to localStorage after getPermissions() succeeds, or add
  rollback logic in the catch block that clears the stored token/userId.


================================ MEDIUM ========================================

BUG #8 — RESERVE TICKET PAGE: STALE SEATING MAP — NEVER REFRESHED
File:       frontend/src/pages/orders/ReserveTicketPage.tsx
Severity:   MEDIUM
Description:
  The seating map is fetched once on component mount and never refreshed.
  If another user books seats while the current user has the page open,
  the current user sees stale availability data. They can select seats
  that appear "available" (green) but are actually already booked.

  The conflict is only discovered at checkout time when the server rejects
  the order, but by then the user has already filled in payment details
  and wasted time.

  Note: The system uses WebSocket only for presence (liveness detection),
  not for real-time data updates. There is no mechanism to push seat
  availability changes to other connected clients.
Fix:
  Either poll the seating map periodically (e.g., every 30 seconds),
  or add a WebSocket channel for seat availability updates, or at minimum
  re-fetch the map when the user clicks "Proceed to Checkout" to validate
  selections before navigating away.

BUG #9 — RESERVE TICKET PAGE: STALE alreadyPurchased COUNT
File:       frontend/src/pages/orders/ReserveTicketPage.tsx
Severity:   MEDIUM
Description:
  The max ticket policy enforcement uses alreadyPurchased, which is fetched
  from historyOrderApi.getUserOrders() once on mount. If the user completes
  a purchase for the same event in another browser tab and returns to this
  tab, the alreadyPurchased count is stale.

  This could allow a user to exceed the per-event ticket limit by
  purchasing in multiple tabs.
Fix:
  Re-fetch the purchase history before proceeding to checkout, or validate
  the ticket count server-side (which should be the primary enforcement
  mechanism regardless).

BUG #10 — EVENTS PAGE: UNHANDLED PROMISE REJECTION + INFINITE SPINNER
File:       frontend/src/pages/events/EventsPage.tsx
Severity:   MEDIUM
Description:
  The getAllActiveEvents() API call has no .catch() handler. If the API
  fails (network error, server error, timeout), the promise rejects as

  Add a .catch() handler that sets an error state and hides the loading
  spinner.

BUG #13 — AUTH CONTEXT: NULL PERMISSIONS CAUSES SILENT TYPEERROR
File:       frontend/src/context/AuthContext.tsx (refreshPermissions, line 68)
Severity:   LOW
Description:
  If authApi.getPermissions() returns null (e.g., malformed API response),
  accessing currentPermissions.userId on line 68 throws a TypeError:
  "Cannot read properties of null (reading 'userId')".

  This error is caught by the inner try-catch block and silently falls
  through to the guest entry flow. No error is logged or surfaced.
  The user ends up as a guest without knowing their existing session
  was invalid.
Fix:
  Add a null guard: if (!currentPermissions) throw new Error('...');
  before accessing properties.
